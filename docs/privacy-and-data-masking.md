# ความเป็นส่วนตัวและการ Mask ข้อมูลภาษาไทย

> **คำเตือนสำคัญ:** การ masking เป็นการลดความเสี่ยง ไม่รับประกันการ anonymization หรือการป้องกันการระบุตัวบุคคลซ้ำได้อย่างสมบูรณ์ ต้องประเมินข้อมูล ชุดข้อมูลที่เชื่อมโยงกัน และกฎหมาย/นโยบายขององค์กรก่อนมี API egress ทุกครั้ง

## ข้อมูลที่ต้องตรวจในบริบทไทย

ตัวตรวจในเครื่องควรครอบคลุมอย่างน้อย:

- ชื่อบุคคลและนามสกุล
- อีเมล และหมายเลขโทรศัพท์
- เลขบัตรประชาชนไทย 13 หลัก รวมการตรวจ checksum
- เลขบัญชีธนาคาร และเลข PromptPay
- ที่อยู่ สถานที่ หรือข้อมูลระบุตำแหน่ง
- รหัสลูกค้า รหัสพนักงาน HN, AN และ case IDs
- ชื่อองค์กร ชื่อโครงการ ความลับทางธุรกิจ และข้อมูลสัญญา

รายการนี้เป็น baseline ไม่ใช่รายการปิดตาย: แต่ละองค์กรต้องเพิ่มรูปแบบรหัสภายในและคำลับของตนเอง โดยไม่ใส่ข้อมูลจริงลงใน repository หรือ test fixture

## กระบวนการหกขั้นตอน

1. **Normalize ในเครื่อง:** ทำ Unicode normalization และแปลงเลขไทย/อารบิกให้ตรวจรูปแบบได้สม่ำเสมอ โดยเก็บต้นฉบับไว้ภายในขอบเขต local เท่านั้น
2. **Detect หลายชั้น:** ใช้ rule และ checksum สำหรับข้อมูลที่มีรูปแบบร่วมกับ Thai-aware NER สำหรับชื่อ ที่อยู่ และบริบทภาษาไทย
3. **แทนด้วย token:** แทนสิ่งที่พบด้วย stable opaque tokens เช่น `[[PERSON:A1]]`; token map ที่ย้อนกลับได้เป็นข้อมูลอ่อนไหวและเก็บในเครื่อง
4. **Preview/approval:** แสดง preview ที่ถูก mask ให้ผู้ใช้ตรวจและอนุมัติก่อน index หรือก่อน API egress ตามตัวเลือก consent
5. **Retrieval:** ทำ retrieval จาก chunk ที่นโยบายอนุญาต โดยลดบริบทเหลือเฉพาะส่วนที่ตอบงานได้
6. **Second pre-egress scan:** scan ซ้ำบน payload สุดท้ายก่อนส่งออก; หาก confidence ต่ำหรือพบข้อมูลที่ยังไม่ mask ให้หยุดส่ง

ตัวอย่างสังเคราะห์เท่านั้น:

```text
ก่อน: ลูกค้า SYNTHETIC_PERSON ติดต่อ SYNTHETIC_PHONE
หลัง: ลูกค้า [[PERSON:A1]] ติดต่อ [[PHONE:B2]]
```

ตัวอย่างข้างต้นไม่ใช่ข้อมูลจริง และตัวอย่าง API ใน repository รับ context ที่ถูก mask แล้วเท่านั้น; ไม่ได้ทำหน้าที่เป็น detector หรือ production masker

## ตัวเลือก consent ก่อนนำเข้า

ให้ผู้ใช้เลือกอย่างชัดเจนก่อนประมวลผลเอกสาร และบันทึกเฉพาะการตัดสินใจ/เวอร์ชันนโยบายที่จำเป็น:

| ตัวเลือก | ผลที่อนุญาต |
| --- | --- |
| **metadata-only** | อ่านเฉพาะ metadata ที่จำเป็น; ไม่สร้าง chunks หรือ embeddings จากเนื้อหา |
| **mask-and-index** | ตรวจและ mask ในเครื่อง แล้วสร้าง index ตาม retention ที่ตกลง |
| **session-only** | ประมวลผลชั่วคราวใน session และล้างข้อมูลที่สร้างขึ้นเมื่อจบ session |
| **cancel** | ไม่อ่าน ไม่ index และไม่ส่งข้อมูลออก |

การเลือก consent ไม่แทนการอนุมัติ masked preview ก่อน egress สำหรับงาน hard และผู้ใช้ต้องเปลี่ยน/ถอน consent ได้โดยมีผลต่อข้อมูลที่เก็บอยู่ตามนโยบายลบข้อมูล

## Retention และการลบข้อมูล

กำหนดอายุข้อมูลและวิธีลบก่อนใช้งานจริง โดยครอบคลุมทุกสำเนา ไม่ใช่เฉพาะไฟล์ที่ผู้ใช้มองเห็น:

| ประเภทข้อมูล | แนวทาง |
| --- | --- |
| Raw files | เก็บเฉพาะเมื่อจำเป็นในเครื่อง; ลบตามคำขอหรือเมื่อครบอายุ พร้อมลบสำเนาชั่วคราว |
| Chunks และ embeddings | ถือว่าอ่อนไหวและอาจรั่วบริบทได้; ลบเมื่อถอน consent/ลบเอกสาร และ rebuild index ที่เกี่ยวข้อง |
| Caches | ใช้ TTL สั้น, เข้ารหัสเมื่อเหมาะสม, และมีคำสั่งล้างที่ตรวจผลได้ |
| Token maps | แยกจาก index, จำกัดสิทธิ์, และลบพร้อมข้อมูลต้นทางตามนโยบาย |
| Logs | เก็บ event, count, policy version และ hash ที่ไม่ย้อนกลับได้; ไม่เก็บ prompt/chunk ดิบหรือ identifiers |
| Backups | ระบุอายุ retention, encryption และขั้นตอนลบ/หมดอายุ เพราะการลบ live data ไม่ลบ backup เอง |

ต้องบันทึกให้ชัดว่าคำสั่งลบครอบคลุม raw files, chunks, embeddings, caches, token maps, logs และ backups เมื่อใด หาก backup ลบไม่ได้ทันที ให้แจ้งช่วงเวลาหมดอายุและจำกัดการ restore ที่อาจนำข้อมูลกลับมา

## ข้อจำกัดและเส้นทางล้มเหลว

- **OCR:** ตัวอักษรอ่านผิด, ตัวเลขไทยแปลงผิด หรือคุณภาพภาพต่ำ อาจทำให้ detector พลาด PII; confidence ต่ำต้อง block egress เพื่อให้คนตรวจ
- **False negative / false positive:** detector อาจพลาดข้อมูลที่ต้อง mask หรือ mask คำปกติจน retrieval เสียคุณภาพ ต้องมี sampling, review และการปรับ rule/NER ในเครื่อง
- **Linkage และ re-identification:** token หรือรายละเอียดที่ดูไม่อ่อนไหวหลายชิ้นอาจเชื่อมกันจนระบุตัวบุคคลได้ จึงต้องทำ context minimization ไม่ใช่ mask เฉพาะ field เดี่ยว
- **Embedding leakage:** embeddings ไม่ใช่ข้อมูลสาธารณะ อาจเผยความหมายหรือใช้อนุมานข้อมูลต้นทางได้ จึงต้องอยู่ในขอบเขต local และใช้ retention/access control
- **Prompt injection:** เอกสารอาจมีคำสั่งมุ่งให้ระบบเปิดเผยข้อมูลหรือข้ามนโยบาย ให้ถือเนื้อหา retrieved เป็น untrusted data แยกจาก system instructions และห้ามมันเปลี่ยน decision gate

หากขั้นใดไม่ผ่าน ห้ามขยาย context หรือใช้ข้อมูลดิบเพื่อแก้ปัญหา หยุดที่ local workflow, แจ้งเหตุแบบ redacted และให้ผู้ใช้เลือกแก้ไข, ตรวจใหม่ หรือ cancel.
